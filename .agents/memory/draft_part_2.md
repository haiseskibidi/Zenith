## 1. Input Handled-State (Ловушка для кликов: как укротить взбесившуюся мышку)

### Суть проблемы на пальцах
Представьте себе жизненную ситуацию. Вы сидите в уютном кафе и листаете меню на планшете. Вы хотите выбрать пиццу и кликаете пальцем по экрану. Но вот незадача: экран планшета оказался прозрачным, и ваш клик не только нажал на кнопку «Заказать», но и проткнул чашку с горячим кофе, стоявшую прямо за планшетом! 

В геймдеве это называется **сквозным кликом (through-click)**. Вы закрываете инвентарь или кликаете по кнопке в меню паузы, а ваш персонаж в этот же миг бьет топором ценный верстак, на который вы навели мышку. Чтобы такого безобразия не происходило, в **Zenith** внедрена система **Input Handled-State** (Состояние обработанного ввода).

### Метафора из жизни
Это работает как классическая двойная дверь в шлюзе. Пока вы не закроете внешнюю дверь (UI-интерфейс), внутренняя дверь (игровой мир) физически заблокирована для любых манипуляций. Клик «поглощается» активным экраном и не летит дальше в глубины игрового пространства.

### Как это реализовано в Java
Давайте посмотрим на красивую и лаконичную схему диспетчеризации ввода в `InputManager`:

```java
// Упрощенный фрагмент логики диспетчеризации кликов в Zenith
public class InputManager {
    private Screen activeScreen; // Наше текущее открытое меню (инвентарь, настройки и т.д.)
    private WorldInteractionSystem worldInteraction; // Класс, отвечающий за разрушение блоков

    public void onMouseClick(double mouseX, double mouseY, int button) {
        // Шаг 1: Сначала спрашиваем активный UI-экран
        if (activeScreen != null) {
            // Передаем координаты мыши и кнопку в интерфейс
            boolean handled = activeScreen.handleMouseClick(mouseX, mouseY, button);
            
            // Если экран сказал: "О, это по моей части! Я обработал этот клик!"
            if (handled) {
                // Прерываем выполнение метода! Клик успешно поглощен интерфейсом
                return; 
            }
        }
        
        // Шаг 2: И только если ни один UI-элемент не перехватил клик...
        // ...мы разрешаем игроку взаимодействовать с кубическим миром
        worldInteraction.performBlockRaycastAndInteract(button);
    }
}
```

**Разбор кода «на пальцах»:**
1. Переменная `activeScreen` хранит ссылку на текущий открытый UI-экран. Если он равен `null`, значит, игрок просто бегает по миру.
2. Метод `handleMouseClick` возвращает логическое значение (`true`/`false`). Это и есть наш **Handled-State**. Если кнопка в инвентаре нажата, возвращается `true`.
3. Оператор `return` мгновенно останавливает метод `onMouseClick`, не давая коду спуститься к строке с `worldInteraction`. Наш верстак в безопасности!

## 2. Matrix Crosshair (Магия SDF: прицел, который умеет дышать)

### Суть проблемы на пальцах
Обычный прицел в играх — это скучная статическая картинка (текстура). Но в современном мире такое решение выглядит уныло. Мы хотим, чтобы прицел реагировал на каждое движение игрока: плавно расширялся при беге, сжимался при прицеливании и пульсировал, когда мы наводим инструмент на слабую точку блока (Weak Spot). 

Передавать сотни текстур под каждое мизерное изменение — безумие для видеопамяти. Поэтому в **Zenith** используется **Matrix Crosshair** — прицел, который рисуется прямо на видеокарте с помощью математики знаковых полей расстояний (**SDF — Signed Distance Fields**).

### Метафора из жизни
Вспомните зрачок живого существа. В темноте или при испуге (бег) он расширяется, чтобы уловить больше света и информации. При ярком свете или концентрации на микроскопической детали (наведение на цель) он сжимается в острую точку. Наш прицел — это такой же математический зрачок, реагирующий на физику персонажа.

### GLSL Шейдер прицела
Давайте заглянем в святая святых — фрагментный шейдер прицела, рисующий идеально гладкое кольцо без единой текстуры:

```glsl
#version 330 core
out vec4 FragColor;
in vec2 TexCoords; // Локальные координаты прицела от -1.0 до 1.0

uniform float uRadius;     // Динамический радиус кольца (меняется от скорости игрока)
uniform float uThickness;  // Толщина линии прицела
uniform vec3 uColor;       // Цвет прицела (например, зеленый или красный при перегреве)

void main() {
    // Шаг 1: Находим расстояние от текущего пикселя до центра прицела (0.0, 0.0)
    float dist = length(TexCoords);
    
    // Шаг 2: Магическая SDF-формула кольца.
    // Вычитаем из расстояния радиус и получаем отклонение. 
    // abs() делает отклонение всегда положительным, а вычитание толщины uThickness
    // формирует саму "трубку" кольца.
    float sdf = abs(dist - uRadius) - uThickness;
    
    // Шаг 3: Сглаживание краев (Antialiasing) «на лету».
    // Функция smoothstep плавно переводит альфа-канал от 1.0 до 0.0 на границе пикселей,
    // полностью убирая «лесенки» (пикселизацию).
    float alpha = smoothstep(0.015, 0.0, sdf);
    
    // Шаг 4: Выводим итоговый пиксель с учетом прозрачности
    FragColor = vec4(uColor, alpha);
}
```

**Разбор кода «на пальцах»:**
1. `length(TexCoords)` считает расстояние по теореме Пифагора: $d = \sqrt{x^2 + y^2}$. Центр экрана имеет координаты $(0,0)$.
2. Формула `abs(dist - uRadius) - uThickness` возвращает отрицательное значение для пикселей, находящихся *внутри* тела кольца, и положительное — *снаружи*.
3. `smoothstep` берет эту разницу и превращает её в плавный градиент прозрачности. Результат — идеально ровные, мягкие края при любом разрешении экрана!

## 3. Mining Heat VFX (Тряска и ярость: как заставить блоки страдать эффектно)

### Суть проблемы на пальцах
Когда вы бьете киркоЙ по прочной скале, вы должны чувствовать её сопротивление. Блок не должен просто безмолвно стоять, пока полоска его здоровья уменьшается. Он должен трястись от ударов, покрываться глубокими ранами-трещинами, а во все стороны должны разлетаться мелкие осколки камня. 

В **Zenith** эта отдача реализована через триаду: **Impact Wobble** (тряска меша блока вдоль нормали удара), **Persistent Scars** (декалы трещин с динамической прозрачностью) и **Classic Voxel Particle System** (воксельные частицы-крошки без физических коллизий).

### Метафора из жизни
Представьте себе спелый арбуз, по которому бьют ложкой. Он упруго вибрирует (тряска), его корка трескается, а во все стороны брызжет сок и летят семечки (частицы). При этом сила брызг напрямую зависит от того, насколько яростно вы замахнулись!

### Вершинный GLSL шейдер деформации блока при ударе
Этот код выполняется на GPU для каждой вершины временного "прокси-меша" повреждаемого блока:

```glsl
#version 330 core
layout (location = 0) in vec3 aPos; // Исходное положение вершины куба
uniform mat4 uModelViewProj;

uniform float uWobbleTime;      // Время, прошедшее с момента удара (в секундах)
uniform float uWobbleForce;     // Начальная амплитуда тряски (зависит от силы удара)
uniform vec3 uImpactNormal;     // Направление удара (вектор нормали грани)

void main() {
    // Шаг 1: Затухание тряски со временем по экспоненциальному закону.
    // exp(-uWobbleTime * 6.0) быстро сводит тряску к нулю.
    float decay = exp(-uWobbleTime * 6.0);
    
    // Шаг 2: Расчет смещения по закону затухающей синусоиды.
    // Частота колебаний высокая (50.0), чтобы блок дрожал с характерным звоном!
    float offset = sin(uWobbleTime * 50.0) * uWobbleForce * decay;
    
    // Шаг 3: Сдвигаем вершины куба ТОЛЬКО в направлении удара (нормали).
    // Это создает иллюзию упругого сжатия блока!
    vec3 dynamicPos = aPos + (uImpactNormal * offset);
    
    // Переводим координаты в экранное пространство
    gl_Position = uModelViewProj * vec4(dynamicPos, 1.0);
}
```

**Разбор кода «на пальцах»:**
1. Вектор `uImpactNormal` указывает, с какой стороны прилетел удар (например, $(0, 1, 0)$ при ударе сверху).
2. Формула `sin(uWobbleTime * 50.0)` отвечает за периодические движения туда-обратно.
3. Множитель `decay` гарантирует, что блок перестанет дрожать через долю секунды, возвращаясь в стабильное состояние.

## 4. Physical Viewmodel (Законы Ньютона в твоих руках: физика пружины для оружия)

### Суть проблемы на пальцах
В старых шутерах оружие в руках персонажа казалось приклеенным к экрану суперклеем. При резком повороте головы оно двигалось абсолютно синхронно с камерой. Выглядит это фальшиво. 

Чтобы руки в **Zenith** ощущались живыми и весомыми, они привязаны к камере не жестко, а через виртуальную **физическую пружину второго порядка** (Mass-Spring-Damper). Тяжелые предметы отстают от взгляда сильнее, а при беге или прыжках руки колеблются с затухающей амплитудой. А если подойти вплотную к стене — персонаж плавно прижмет локти к телу, чтобы не проткнуть топором кирпичи (**Tactical Tuck**).

### Метафора из жизни
Представьте, что вы держите в руке тяжелую чугунную сковородку на длинной резиновой ручке. Если вы резко повернетесь всем телом, сковородка сначала отстанет, прочертив дугу в воздухе, а затем с небольшим перелетом (overshoot) вернется в исходное положение перед вами.

### Математический симулятор физической пружины в Java
Вот как описываются движения рук игрока с помощью дифференциального уравнения второго порядка:

```java
public class Spring3D {
    public float currentX, currentY, currentZ; // Текущее положение руки в пространстве вида
    public float velX, velY, velZ;             // Текущие скорости по осям
    public float targetX, targetY, targetZ;     // Целевая точка (куда рука стремится)

    // Параметры физической системы (задаются в конфигурации JSON)
    public float stiffness = 160.0f; // Жесткость пружины (как быстро рука возвращается)
    public float damping = 14.0f;     // Коэффициент затухания (вязкое трение воздуха)

    public void update(float deltaTime) {
        // Ограничиваем шаг времени, чтобы при лагах физика не "взорвалась"
        float dt = Math.min(deltaTime, 0.03f);

        // Расчет силы пружины Гука по оси X: F = -k * x
        float forceX = (targetX - currentX) * stiffness;
        // Расчет силы вязкого сопротивления среды: F_damp = -d * v
        float dampX = velX * damping;
        
        // Ускорение (сила минус сопротивление при массе m = 1.0f)
        float accX = forceX - dampX;

        // Интегрируем скорость и позицию (Метод Эйлера-Кромера)
        velX += accX * dt;
        currentX += velX * dt;

        // Аналогичные расчеты для осей Y и Z
        float forceY = (targetY - currentY) * stiffness;
        float dampY = velY * damping;
        float accY = forceY - dampY;
        velY += accY * dt;
        currentY += velY * dt;

        float forceZ = (targetZ - currentZ) * stiffness;
        float dampZ = velZ * damping;
        float accZ = forceZ - dampZ;
        velZ += accZ * dt;
        currentZ += velZ * dt;
    }

    // Метод экстренного сброса при смене оружия, чтобы топор не летел через весь экран
    public void reset(float tx, float ty, float tz) {
        this.currentX = tx;
        this.currentY = ty;
        this.currentZ = tz;
        this.velX = 0;
        this.velY = 0;
        this.velZ = 0;
        this.targetX = tx;
        this.targetY = ty;
        this.targetZ = tz;
    }
}
```

**Разбор кода «на пальцах»:**
1. Разность `(targetX - currentX)` — это растяжение нашей виртуальной пружины. Чем сильнее мы дернули мышку, тем больше эта разность, и тем сильнее пружина «тянет» руку обратно.
2. `velX * damping` — это тормоз. Без него пружина колебалась бы бесконечно, как безумный маятник. Вязкое трение гасит излишки кинетической энергии.
3. Ограничение `Math.min(deltaTime, 0.03f)` спасает от багов: если игра зависнет на полсекунды, расчетное ускорение не улетит в космос, превратив координаты в `NaN`.

## 5. Minimap Radar (Тактический сонар: как видеть ушами сквозь стены)

### Суть проблемы на пальцах
В кубическом мире **Zenith** звук играет ключевую роль. Монстры слышат ваши шаги, работу ваших механизмов и рубку деревьев. Чтобы игрок визуально понимал, насколько он шумит и откуда исходит потенциальная опасность, на экран выводится тактический радар-сонар. 

Он работает полностью на процедурных шейдерных эффектах: испускает расходящиеся круги звуковых волн, которые при соприкосновении с источниками шума подсвечивают их яркими импульсными метками.

### Метафора из жизни
Представьте тихий пруд ночью. Вы бросаете в воду камень — от него расходятся идеальные концентрические круги. Если на поверхности воды плавает поплавок (источник шума/монстр), проходящая волна заколышет его, заставив выдать ответные мелкие волны. Радар делает то же самое на экране вашего планшета.

### GLSL Шейдер процедурного сонара
Давайте посмотрим, как видеокарта рисует волну сонара и отметку источника шума:

```glsl
#version 330 core
out vec4 FragColor;
in vec2 uV; // Координаты текстуры радара от -1.0 до 1.0 (центр в 0.0)

uniform float uTime;          // Глобальное время для анимации движения волн
uniform vec2 uNoiseSource;    // Положение источника звука (например, крадущегося монстра)
uniform float uPlayerNoise;   // Текущий уровень шума игрока (радиус расхождения волны)

void main() {
    // Шаг 1: Вычисляем расстояние от центра радара
    float distToCenter = length(uV);
    
    // Шаг 2: Генерируем круговую волну, бегущую от центра
    // mod(uTime, 1.0) зацикливает анимацию волны от 0 до 1
    float waveRadius = mod(uTime * 0.8, 1.0) * uPlayerNoise;
    
    // Формируем тонкую светящуюся полосу волны сонара
    float wave = smoothstep(0.03, 0.0, abs(distToCenter - waveRadius));
    
    // Шаг 3: Вычисляем расстояние от текущего пикселя до источника шума (монстра)
    float distToMonster = length(uV - uNoiseSource);
    
    // Создаем яркую круглую точку для монстра
    float monsterMarker = smoothstep(0.06, 0.0, distToMonster);
    
    // Шаг 4: Метка монстра становится видимой ТОЛЬКО тогда, когда её настигает волна!
    float isSwept = step(distToCenter, waveRadius + 0.05); 
    float finalMonsterIntensity = monsterMarker * isSwept * (1.0 - waveRadius);
    
    // Смешиваем цвета: неоновый зеленый для волны радара + тревожный красный для монстра
    vec3 waveColor = vec3(0.0, 1.0, 0.4) * wave * 0.4;
    vec3 monsterColor = vec3(1.0, 0.1, 0.1) * finalMonsterIntensity * 1.0;
    
    float finalAlpha = wave * 0.4 + finalMonsterIntensity * 0.9;
    
    FragColor = vec4(waveColor + monsterColor, finalAlpha);
}
```

**Разбор кода «на пальцах»:**
1. Выражение `abs(distToCenter - waveRadius)` вычисляет расстояние до гребня бегущей волны. С помощью `smoothstep` мы заставляем светиться только узкую полоску на этом гребне.
2. Функция `step(a, b)` возвращает `1.0`, если $a < b$, и `0.0` в противном случае. Она работает как жесткий переключатель: «волна сонара дошла до цели — показать красную точку».
3. Множитель `(1.0 - waveRadius)` постепенно гасит интенсивность засвета по мере удаления волны от эпицентра.

## 6. Contextual Interaction (Интуитивный клик: швейцарский нож игрового интерфейса)

### Суть проблемы на пальцах
Представьте игру, где для каждого действия нужно открывать инвентарь или контекстное меню: «Открыть инвентарь -> Выбрать топор -> Выбрать пень -> Нажать "Положить бревно на пень"». Это утомляет и портит погружение. 

В **Zenith** реализована система контекстного взаимодействия. Игра сама понимает, что вы хотите сделать, анализируя три фактора: на какой блок вы смотрите, что лежит у вас в руках, и в каком состоянии находится этот блок. Вся информация мгновенно выводится в аккуратный контекстный HUD.

### Метафора из жизни
Представьте, что вы подошли к двери с тяжелыми пакетами в руках. Дверь оборудована умным датчиком: она видит, что ваши руки заняты, и автоматически распахивается. Если вы подходите с пустыми руками — она ждет, пока вы нажмете на ручку. Система подстраивается под ваши физические условия.

### Код выбора контекста взаимодействия в Java
Вся логика аккуратно разложена в `InteractionSystem`:

```java
public class InteractionSystem {
    
    public ContextualPrompt evaluateInteraction(Player player, BlockPos targetPos) {
        World world = player.getWorld();
        BlockState state = world.getBlockState(targetPos);
        ItemStack heldItem = player.getHeldItem();
        
        // Сценарий А: Мы смотрим на колоду для рубки (Stump)
        if (state.is(Blocks.STUMP)) {
            // Если в руках топор
            if (heldItem.is(Items.AXE)) {
                return new ContextualPrompt("ЛКМ: Рубить заготовку", PromptType.CRAFT);
            }
            // Если руки пусты, а на пне лежит готовое полено
            if (heldItem.isEmpty() && state.hasComponent(ContainerComponent.class)) {
                return new ContextualPrompt("ПКМ: Забрать полено", PromptType.INTERACT);
            }
            // Если в руке бревно, которое можно положить на колоду
            if (heldItem.is(Items.LOG)) {
                return new ContextualPrompt("ПКМ: Положить бревно на колоду", PromptType.PLACE);
            }
        }
        
        // Сценарий Б: Мы смотрим на куст диких ягод
        if (state.is(Blocks.BERRY_BUSH)) {
            if (state.get(BerryBushBlock.AGE) == 3) { // Куст созрел
                return new ContextualPrompt("ПКМ: Собрать ягоды", PromptType.HARVEST);
            }
        }

        // Если вариантов взаимодействия нет - возвращаем null (HUD чист)
        return null;
    }
}
```

**Разбор кода «на пальцах»:**
1. Метод `evaluateInteraction` постоянно опрашивается на клиенте, когда игрок наводит прицел на интерактивные объекты.
2. Проверка `state.is(Blocks.STUMP)` мгновенно отсекает ненужные вычисления, если перед нами обычная земля или камень.
3. Класс `ContextualPrompt` содержит текст подсказки и тип действия (для смены цвета и иконки на экране). Игрок всегда точно знает, какая кнопка за что отвечает!

## 7. AAA Graphics MSAA 4x (Кинематографический глянец: плавная интерполяция и сглаживание)

### Суть проблемы на пальцах
Многие инди-игры грешат противным подергиванием картинки при движении камеры. Физика в мире считает координаты с фиксированной частотой (например, 20 тиков в секунду или 170 тиков в секунду), а монитор работает на частоте 144 Гц или 240 Гц. Если обновлять картинку строго по физическим тикам — вы получите рваное слайд-шоу. 

В **Zenith** эта проблема решена на уровне **AAA-архитектуры интерполяции**: физика и рендер полностью разделены. Физический движок считает шаги в своем темпе, а рендерер вычисляет промежуточное положение камеры и объектов между кадрами с помощью коэффициента `alpha`. А сглаживание **MSAA 4x** и анизотропная фильтрация сглаживают пиксельные ребра блоков, делая картинку невероятно чистой.

### Метафора из жизни
Представьте себе мультфильм. Художник-аниматор нарисовал всего 10 ключевых кадров бега персонажа (физические тики). Но хитрый проектор прогоняет пленку через специальный процессор, который плавно дорисовывает промежуточные фазы движения между этими кадрами, превращая дерганый мультик в плавное кино.

### Код вычисления коэффициента интерполяции
Давайте разберем, как рендер-петля вычисляет точный коэффициент смешивания временных промежутков:

```java
public class RenderEngine {
    private double physicsTickIntervalNs = 1_000_000_000.0 / 170.0; // Длина физического тика (~5.88 мс при 170Hz)
    private long lastPhysicsTickTimeNs; // Системное время последнего физического обновления

    public float calculateInterpolationAlpha() {
        long currentTimeNs = System.nanoTime();
        
        // Сколько наносекунд прошло с момента последнего тика физики
        long elapsedNs = currentTimeNs - lastPhysicsTickTimeNs;
        
        // Находим отношение прошедшего времени к полному интервалу тика
        float alpha = (float) (elapsedNs / physicsTickIntervalNs);
        
        // Жестко зажимаем значение в диапазон [0.0; 1.0], чтобы избежать артефактов экстраполяции
        return Math.clamp(alpha, 0.0f, 1.0f);
    }
    
    public void renderEntity(Entity entity, float alpha) {
        // Вычисляем плавное положение объекта на экране!
        // Формула: Lerp(prev, current, alpha)
        double interpolatedX = entity.prevX + (entity.currentX - entity.prevX) * alpha;
        double interpolatedY = entity.prevY + (entity.currentY - entity.prevY) * alpha;
        double interpolatedZ = entity.prevZ + (entity.currentZ - entity.prevZ) * alpha;
        
        // Рисуем модельку по интерполированным координатам
        drawModelAt(interpolatedX, interpolatedY, interpolatedZ);
    }
}
```

**Разбор кода «на пальцах»:**
1. `physicsTickIntervalNs` — это эталонная длина шага физики в наносекундах. На частоте 170 Гц один тик длится около 5.88 миллисекунд.
2. `alpha` показывает, насколько близко мы подобрались к следующему физическому тику. Если мы ровно посередине — `alpha = 0.5`.
3. Формула `entity.prevX + (entity.currentX - entity.prevX) * alpha` — это классическая линейная интерполяция (**Lerp**). Она плавно двигает объект по экрану на каждый кадр рендеринга, даже если FPS равен 360, а физика считает координаты всего 170 раз в секунду.

## 8. Settings & Input (Чертежи интерфейса: декларативный JSON против спагетти-кода)

### Суть проблемы на пальцах
Хардкодить координаты кнопок, размеры окон и раскладку клавиш прямо в коде Java — это страшный грех, ведущий к хаосу. Если вы захотите перенести кнопку «Настройки» на 10 пикселей влево, вам придется перекомпилировать весь проект. 

В **Zenith** все интерфейсы и настройки полностью **Data-Driven**. Они описываются декларативно в JSON-файлах. Специальный движок верстки `InventoryLayout` считывает этот файл, строит рекурсивное дерево зависимостей, рассчитывает адаптивные фоны и расставляет кнопки на экране в зависимости от текущего разрешения.

### Метафора из жизни
Представьте себе конструктор LEGO. Вместо того чтобы намертво склеивать детали суперклеем, вы собираете их по инструкции на штифтах. Если вам захочется заменить крышу или переставить окно, вы просто берете другую деталь и ставите её на место по чертежу, не разрушая фундамент дома.

## 9. Викторина для архитекторов воксельных миров!
*Проверьте свои знания архитектурных тонкостей Zenith. Впереди два чертовски каверзных вопроса!*

### Вопрос №1: Влияние инерции и предотвращение «взрывов» физики пружины
**Почему при резком повороте камеры в Zenith тяжелый топор отстает от перекрестия сильнее, чем легкий нож, и как пружинный симулятор предотвращает "взрыв" физики при быстрой смене предметов?**

1. Из-за динамического изменения `LOD_BIAS` тяжелых мешей; движок сбрасывает пружину через метод `clear()`.
2. Из-за влияния параметра `weight` (массы) на затухание и частоту пружины второго порядка; стабильность при смене обеспечивается вызовом метода `reset()`, который мгновенно совмещает координаты пружины с целевой точкой.
3. Из-за рендеринга через прокси-меши с флагом `uIsProxy`; взрывы предотвращаются ограничением `breakDelayTimer`.
4. Из-за распределения суставов (Shoulder 70%, Hand 10%) в скелетной иерархии; пружина гасится побитовой маской `& 0x7F`.

**Правильный ответ:** **2** (индекс 1 в JS-массиве).

**Подробнейшее объяснение:**
В физическом симуляторе пружины-массы-демпфера второго порядка масса предмета напрямую влияет на частоту собственных колебаний системы: $\omega_0 = \sqrt{\frac{k}{m}}$. У тяжелого топора параметр `weight` больше, следовательно, его виртуальная масса $m$ выше, что снижает частоту колебаний и делает движение более инертным и «тягучим». Рука медленнее догоняет взгляд игрока. 
Однако, если игрок мгновенно переключается на другой предмет, целевая точка пружины резко меняется на противоположную в координатах вида (View-space). Из-за огромного расстояния между текущим и новым положением пружины сила упругости $F = -k \cdot x$ мгновенно становится колоссальной, что на следующем шаге интегрирования `vel += acc * dt` порождает гигантскую скорость и приводит к числовой нестабильности (координаты улетают в бесконечность — пружина «взрывается»). Метод `reset()` решает эту проблему хирургически: он обнуляет скорости пружины и мгновенно телепортирует координаты пружины в целевую точку нового предмета, гася любые паразитные импульсы.

### Вопрос №2: Сглаживание высокогерцовых мониторов и Z-буферизация
**Каким образом Zenith решает проблему "дерганья" (micro-stuttering) объектов и камеры при фиксированной физике в 170 тиков в секунду (Fixed-UPS) на высокогерцовых мониторах (например, 240 Гц), и зачем нужно разделение флагов `transparent` и `translucent`?**

1. Частота физики динамически подстраивается под FPS; флаги разделяют Z-буфер по методу `glPolygonOffset`.
2. Рендерер рассчитывает коэффициент `alpha = accumulator / interval` и линейно интерполирует позиции между предыдущим тиком (`prevPosition`) и текущим тиком, а разделение флагов позволяет объектам без Z-записи попадать в Blending Pass, исключая X-ray баги границ.
3. Движок отключает гравитацию через `Ground Locking` и пересчитывает чанки в фоновом режиме; флаги оптимизируют вызовы `glDrawElementsInstanced`.
4. Координаты переводятся в 3D массивы текстур `GL_TEXTURE_2D_ARRAY` с LOD_BIAS; флаги маскируют невидимые грани с помощью `faceMask`.

**Правильный ответ:** **2** (индекс 1 в JS-массиве).

**Подробнейшее объяснение:**
Поскольку частота монитора (240 Гц) выше частоты физического движка (170 Гц), без интерполяции некоторые кадры рендеринга будут отображать одни и те же физические координаты, создавая микро-дерганья (stuttering). Zenith решает это, разделяя физический поток и рендер-поток: в рендере вычисляется коэффициент `alpha`, который показывает, какая часть физического тика уже завершилась. На основе `alpha` позиции всех визуальных моделей сглаживаются между их прошлым и текущим состояниями.
Разделение флагов `transparent` (прозрачность на уровне формы, например плиты или решетки) и `translucent` (полупрозрачность материала, например стекла или воды) критически важно для рендеринга. Блоки с флагом `transparent` не содержат полупрозрачных цветов, поэтому они могут рендериться в **Opaque Pass** с записью в Z-буфер (Z-write включен) для экономии производительности (видеокарта сама отсекает невидимые пиксели). А полупрозрачные блоки `translucent` должны рендериться строго после непрозрачных в специальном **Blending Pass** (смешивание цветов) БЕЗ записи в Z-буфер (только Z-read), иначе окантовки и грани полупрозрачных кубов перекроют друг друга, создавая некрасивые артефакты прозрачности (X-ray сквозь воду или стекло).
