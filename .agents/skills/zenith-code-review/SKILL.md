# Zenith Code Review Skill

Этот навык предназначен для проведения специализированного, глубокого и подробного обзора кода в проекте Zenith. Он заменяет универсальные гайдлайны на строгие проектные мандаты, оптимизированные под высокопроизводительный 3D воксельный движок на Java 21 + OpenGL.

---

## 1. Zero-Allocation Mandate (Горячие пути)

Методы рендеринга (`render`), обновления кадров (`update`, `tick`), симуляции сущностей (`move`) и генерации чанков/мешей выполняются десятки и тысячи раз в секунду. Выделение памяти на куче (heap allocations) в этих путях приводит к GC-фризам и падению FPS.

### Чек-лист проверок:
- **Запрет на инстанцирование JOML-объектов**:
  - Никаких `new Vector3f()`, `new Vector2f()`, `new Vector3d()`, `new Matrix4f()` или `new AABB()`.
  - Вместо `new` брать объекты из контекста рендера: `RenderContext.getVector()` или `RenderContext.getMatrix()`.
  - Либо передавать вектор-приемник в сигнатуру метода (например, `getInterpolatedPosition(float alpha, Vector3f dest)`).
  - В синглтонах или долгоживущих менеджерах (как в `AtmosphereManager`) кэшировать цвета и вектора в виде `private final Vector3f` полей и обновлять их на тиках с помощью `.set()`, не создавая новые объекты.
- **Примитивный доступ к координатам AABB**:
  - Запрещено вызывать `aabb.getMin()` или `aabb.getMax()`, так как они создают и возвращают новые `Vector3f` на куче.
  - Использовать примитивные геттеры: `aabb.minX()`, `aabb.maxX()`, `aabb.minY()`, `aabb.maxY()`, `aabb.minZ()`, `aabb.maxZ()`.
- **Запрет на выделение массивов при генерации мешей**:
  - Никаких `new float[]` или `new float[][]` для вершин граней вокселя в `ChunkMeshGenerator`.
  - Использовать переиспользуемый ThreadLocal буфер `tempFaceVertices` внутри `MeshData` для вычисления вершин на лету.
- **Обход коллекций без создания итераторов**:
  - В горячих методах (например, притяжение и слияние предметов в `ItemEntity.tryMerge`) запрещено использовать стандартный `foreach` для `ArrayList`, так как он неявно создает объект `Iterator` на куче.
  - Использовать классические циклы `for (int i = 0; i < list.size(); i++)`.
- **Справочные материалы**:
  - См. детальные шаблоны оптимизации в [Heap Optimization Guide](file:///.agents/skills/zenith-code-review/references/heap_optimization.md).

## 2. Component-Based Architecture (Lite ECS)

В Zenith запрещено использовать глубокое наследование для добавления новых типов блоков или предметов.

### Чек-лист проверок:
- **Запрет на `instanceof` для контента**:
  - Запрещено писать `if (item instanceof ToolItem)` или `if (block instanceof ChestBlock)`.
  - Все предметы являются экземплярами `Item`, а блоки — `BlockDefinition`. Их поведение настраивается динамически.
  - Для проверки свойств использовать компоненты: `item.getComponent(ToolComponent.class)` для предметов или `def.getComponent(ContainerComponent.class)` для блоков.
- **Модульные блоки с состоянием (ModularBlockEntity)**:
  - Вместо создания специализированных классов `BlockEntity` использовать универсальный `ModularBlockEntity`, считывающий компоненты (`container`, `crafting_surface`) из JSON блока.
  - В методах `update(float deltaTime)` любых `BlockEntity`, реализующих `ITickable`, на первой же строчке обязательна проверка на инициализацию мира: `if (world == null) return;`.
- **Справочные материалы**:
  - См. примеры правильной структуры компонентов в [Component Patterns](file:///.agents/skills/zenith-code-review/examples/component_examples.md).

## 3. Data-Driven Development (Никакого хардкода)

Все параметры игрового контента, рецептов, генерации рельефа и физики должны быть вынесены в JSON.

### Чек-лист проверок:
- **Регистрация через реестры**:
  - Числовые ID назначаются движком динамически при загрузке. Запрещено использовать жестко закодированные ID.
  - Обращение к ресурсам должно происходить по `Identifier.of("zenith:path")`.
- **Статические холдеры**:
  - Для быстрого обращения к блокам и предметам в Java-коде использовать статические поля-холдеры в классах `Blocks` и `Items`, которые заполняются автоматически через рефлексию. Имена полей в верхнем регистре (SNAKE_CASE) должны точно совпадать с путями JSON-файлов.
- **Валидация целостности (.index)**:
  - Добавление файлов в игру должно сопровождаться регистрацией их имен в соответствующих файлах индекса `.index` (например, `journal/entries/.index`).

## 4. Битовые маски для метаданных (Metadata Masking)

Для хранения состояний блоков (направление, тип, естественность) используется 1 байт метаданных. 

### Чек-лист проверок:
- **Запрет на сравнение метаданных целиком**:
  - Запрещено писать `if (metadata == 2)`. Необходимо использовать битовые маски.
  - Маска `0x07` (0000 0111) используется для извлечения направления вращения (0-5).
  - Маска `0x80` (1000 0000) определяет флаг `BIT_NATURAL` (обозначающий, что блок был сгенерирован миром, а не поставлен игроком).
  - Маска `0x7F` (0111 1111) используется для игнорирования флага `BIT_NATURAL` и получения индекса древесины в `TreecapitatorService` или `WoodTypeRegistry`.

## 5. Графика, Прозрачность и Wobble

- **Разделение прозрачности**:
  - Неполные блоки (плиты, заборы), которые не заполняют весь кубический воксель, должны иметь параметр `"transparent": true` в JSON и рендериться в **Opaque Pass** с записью в Depth Buffer.
  - Полупрозрачные блоки (стекло, вода) должны иметь параметры `"transparent": true, "translucent": true` в JSON и рендериться в самом конце в **Translucent Pass** без записи в Depth Buffer для альфа-смешивания.
- **Анимация колыхания блока (Wobble)**:
  - При рендеринге оверлеев разрушения (шрамов) и контура выделения блоков обязательно загружать и передавать в вершинный шейдер параметры качания (`uWobbleScale`, `uWobbleOffset`, `uWobbleShake`, `uWobbleTime`) из профиля анимации блока, чтобы оверлеи не рассинхронизировались и не отставали от самого блока.

## 6. Геймплейная физика, Ввод и Дискретность

- **Дискретность взаимодействия**:
  - При взаимодействии с кастомными блоками (например, обтёсывание пня ножом) проверять флаг `isNewClick`. 1 клик ЛКМ должен строго соответствовать 1 действию (1 вырезанному сегменту), зажатие кнопки мыши не должно вызывать лавинообразное срабатывание логики.
- **Ввод без хардкода**:
  - Запрещено использовать GLFW клавиши напрямую. Опрашивать абстрактные действия из `InputManager` (например, `isActionPressed("move_forward")`).
- **Безопасный Step-Up**:
  - Автоподъем сущностей по ступеням (`StepUpHandler`) должен обязательно выполнять проверку коллизий с потолком (ceiling collision check), ограничивая высоту подъема, чтобы сущность не проталкивалась сквозь низкие перекрытия (например, балки шахт).

## 7. Асинхронное освещение и Погода

- **Конвейер LightEngine**:
  - Обновление света должно происходить асинхронно через `enqueueLightUpdate(pos)`. 
  - Синхронное обновление света разрешено только в режиме Fast-path (когда очередь пуста, фоновая задача не активна и мы не превысили лимит до 5 синхронных обновлений в тике длительностью 20 мс), чтобы исключить лаг при быстром разрушении блоков.
  - При генерации мира следить за Queue Guard: если размер очереди превышает 16384, очередь очищается для предотвращения RAM-фрагментации.
- **Погода и туман**:
  - Рассчитывать погоду только на CPU (`WeatherManager`) и передавать интенсивность дождя (`currentRainIntensity`) на GPU.
  - Переходы интенсивности дождя и рассеивания тумана должны быть абсолютно плавными во времени.

## 8. Сетевое взаимодействие (Kryonet)

- **TCP vs UDP**:
  - Высокочастотные и некритичные для надежности пакеты (положение игрока `PlayerPositionPacket`, направление взгляда) должны отправляться по UDP (`client.sendUDP(packet)`).
  - Важные и требующие гарантированной доставки пакеты (изменение блоков `BlockUpdatePacket`, системные действия, чат-сообщения) должны отправляться строго по TCP (`client.sendTCP(packet)`).
- **Регистрация пакетов**:
  - Каждый новый сетевой пакет должен быть зарегистрирован в Kryo-инстансах в `GameClient.registerPackets()` и `GameServer.registerPackets()`.

## 9. Чистота кодовой базы и сдача кода (Clean Code & Git)

- **Лимит строк (Surgical Refactoring)**:
  - Длина любого создаваемого или изменяемого файла должна стремиться к размеру **до 250 строк**.
  - Если разделение файла искусственно разрушает связность логики или размывает архитектурный фокус, допускается размер в пределах **250-500 строк**. В этом случае агент обязан аргументировать пользователю, почему декомпозиция ухудшит кодовую базу (Pushback). Превышение свыше 500 строк без согласования запрещено.
- **Навигация по соседям**:
  - Запрещено хардкодить массивы смещений `int[][] offsets`. Использовать перечисление `Direction`.
- **Запрет на использование версионных обозначений (v1.0, v4.2 и т.п.)**:
  - В проекте Zenith запрещено использовать версионные суффиксы для подсистем, файлов, планов, коммитов или комментариев (например, "v1.0", "v2.0", "v4.2"). Единственная разрешенная версия — это общая версия всей игры, которой на данный момент нет.
- **Obsidian и Git сообщения**:
  - Описание коммита в Git пишется строго на английском языке (например, `feat: add sound occlusion support`).
  - Перед коммитом обязательно передавать русское описание изменений через переменную окружения `OBSIDIAN_MSG` (например, `$env:OBSIDIAN_MSG="Добавлено поглощение звуков"; git commit -m "..."`).
