# Глава 7. Асинхронные вычисления & Многопоточность

В этой главе мы разберем одну из самых сложных тем в программировании высоконагруженных систем — **Многопоточность (Concurrency)**. Вы узнаете, как устроен асинхронный конвейер генерации чанков, как рассчитывать 3D-освещение в фоне и как реализовать Lock-Free структуры данных для защиты от повреждения памяти.

---

## 1. Асинхронный конвейер чанков в Zenith

В воксельном мире мир бесконечен. Игрок бежит вперед, из-за чего перед ним постоянно должны появляться новые чанки, а старые — выгружаться. 

Если генерировать ландшафт и строить 3D-меши чанков в главном игровом потоке, игра превратится в пошаговую стратегию. Генерация 3D-шума Simplex Noise и Greedy Meshing одной секции чанка занимают около 10-50 мс. В главном потоке это вызвало бы пропуск кадров и дикие лаги.

В Zenith v2.5 весь конвейер вынесен в **пулы асинхронных потоков**:

```
  Главный Поток (Рендеринг)      ChunkGenExecutor (Асинхронный)
  ┌────────────────────────┐      ┌──────────────────────────────┐
  │  Render Loop (200 FPS) │      │  Thread 1: Генерация Шума    │
  │                        │      │  Thread 2: Построение Меша   │
  │  Запрос Чанка ────────┼─────>│                              │
  │  Отрисовка готовых <───┼──────│  Запись в MeshPool (VRAM)    │
  └────────────────────────┘      └──────────────────────────────┘
```

### 1.1 Архитектура пулов потоков (`chunkGenExecutor`)
Мы используем специализированный `ThreadPoolExecutor` с жесткими ограничениями:
*   Количество потоков ограничено `Runtime.getRuntime().availableProcessors() - 1`, чтобы один поток всегда оставался свободным для главного цикла рендеринга и операционной системы.
*   **Radial Spiral Priority (Приоритетная спираль)**: Задачи на генерацию мешей постоянно пересортировываются в очереди по дистанции до игрока. Чанки, которые находятся прямо перед носом игрока, мешатся в первую очередь, а чанки на границе видимости ждут своей очереди. Это полностью исключает визуальные дыры под ногами при резких разворотах камеры.

## 2. Асинхронное освещение в `LightEngine`

Распространение 3D-света в кубическом мире работает по алгоритму **BFS (Breadth-First Search / Обход в ширину)**. При установке факела свет растекается во все 6 сторон на расстояние 15 блоков, затухая на 1 уровень с каждым шагом.

При массовом изменении ландшафта (например, взрыве или срубании дерева) приходится пересчитывать миллионы световых вершин. Этот процесс полностью асинхронен и управляется пулом `lightExecutor`.

### 2.1 Проблема гонок данных (Data Races)
Когда один поток (асинхронный свет) читает типы блоков в мире, а другой поток (главный цикл игрока) в этот же момент меняет блок (игрок выкопал землю), возникает **Data Race (гонка данных)**. 
Поток света может считать некорректное состояние, уйти в бесконечную рекурсию и вызвать зависание игры.

### 2.2 Boundary & Generation Safety (Безопасность границ)
Для предотвращения зависаний в `LightEngine` внедрена система защиты:
1.  **world.isGenerating()**: Во время первичной генерации ландшафта (когда мир создает терабайты блоков за раз) асинхронные расчеты света временно отключаются. Свет рассчитывается один раз в самом конце, "начисто", что экономит 90% ресурсов процессора.
2.  **Boundary Safety (Проверка границ)**: Перед тем как прочитать соседний блок, поток света проверяет через быстрый побитовый кэш: *загружен ли целевой чанк сейчас?* Если чанк выгружается, задача по свету на границе чанка мгновенно останавливается, предотвращая утечки памяти и обращение к `null`.

## 3. Lock-Free Chunk Integrity & Palette Corruption Guard

Самая опасная уязвимость многопоточных воксельных движков — **повреждение палитры чанка (Palette Corruption)**.

### 3.1 Что такое Палитра Чанка
Чтобы экономить оперативную память, чанк не хранит объекты `Block` для каждого из $16 \times 16 \times 16 = 4096$ вокселей.
Он хранит:
1.  **Палитру (Palette)** — динамический список уникальных типов блоков, присутствующих в чанке: `[0: AIR, 1: GRASS, 2: DIRT]`.
2.  **Массив индексов (`short[]`)** — 4096 чисел, каждое из которых указывает на индекс в палитре.

```
  Массив Индексов (short[4096])          Палитра Чанка (ArrayList)
  ┌───────────────────────────┐          ┌───────────────────────┐
  │  [ 0, 1, 1, 2, 0, 1, 2 ]  ├─────────>│  Index 0: zenith:air  │
  └───────────────────────────┘          │  Index 1: grass_block │
                                         │  Index 2: dirt        │
                                         └───────────────────────┘
```

### 3.2 Суть бага Palette Corruption
Представь сценарий:
1.  **Асинхронный поток мешера** начинает строить 3D-модель чанка. Он считывает массив индексов и лезет в палитру чанка, чтобы узнать текстуру блока: `palette.get(index)`.
2.  В этот же микросекундный момент **Главный поток** (игрок) ставит новый блок, которого раньше не было в чанке (например, факел). 
3.  Палитра расширяется: `palette.add(torch)`. Внутри структуры `ArrayList` происходит переаллокация внутреннего массива.
4.  Асинхронный поток считывает индекс старой палитры, но из-за переаллокации в памяти получает выход за границы массива (**`ArrayIndexOutOfBoundsException`**) или сдвинутый индекс. 

В результате JIT-компилятор вылетает с ошибкой `ACCESS_VIOLATION`, игра аварийно закрывается, а файл сохранения мира повреждается.

### 3.3 Решение: Lock-Free `Palette Corruption Guard`
Для решения этой проблемы в Zenith `Chunk.java` использует гибридную Lock-Free защиту:
1.  **Lock-Free Read / Synchronized Write**: Чтение блоков мешером происходит абсолютно без блокировок (чтобы не тормозить FPS). Но запись новых блоков в палитру всегда жестко синхронизирована через монитор `synchronized(paletteLock)`.
2.  **Palette Corruption Guard**: Метод `getSnapshot()` перед генерацией меша проверяет целостность данных. Если из-за микросекундного рассинхрона считанный индекс вокселя выходит за пределы размера текущей палитры, этот индекс **автоматически сбрасывается в безопасный `0` (AIR)**, предотвращая вылет JVM, а в лог пишется предупреждение:

```java
// com.za.zenith.world.chunks.Chunk.java
public int getBlockTypeSafe(int index) {
    int paletteIndex = indexData[index];
    
    // Palette Corruption Guard
    if (paletteIndex < 0 || paletteIndex >= palette.size()) {
        System.err.println("[WARN] Palette Corruption detected at index " + index + "! Auto-restoring to AIR.");
        return 0; // Безопасный возврат воздуха
    }
    
    return palette.get(paletteIndex);
}
```
Это позволило полностью стабилизировать асинхронный мешинг и навсегда избавиться от случайных крашей игры при быстром беге и копании блоков.

## 4. Подготовка к собеседованию (IT-Шпаргалка)

### Вопрос 1: В чем разница между ключевым словом `synchronized`, классом `ReentrantLock` и атомарными переменными (`AtomicInteger`) в Java? Когда что использовать?
*   **Ответ**: 
    *   **`synchronized`** — это встроенный в JVM механизм взаимного исключения (Mutual Exclusion). Он привязан к монитору объекта. При входе в блок поток захватывает монитор. Если монитор занят, поток блокируется и переходит в состояние `BLOCKED` (засыпает), передавая управление операционной системе.
        *Использование*: Подходит для простых критических секций записи (например, расширение палитры чанка), когда операции редки и не влияют на горячий FPS.
    *   **`ReentrantLock`** — это класс из `java.util.concurrent.locks`. Предоставляет более гибкий контроль: поддерживает попытки захвата блокировки с таймаутом (`tryLock()`), опрос состояния, честные очереди и несколько условий ожидания (Condition). Построен на базе AQS (AbstractQueuedSynchronizer).
        *Использование*: Для сложных многопоточных систем (например, сетевой буфер или очередь задач генерации мира).
    *   **Атомарные переменные (`AtomicInteger`, `AtomicReference`)** не используют системные блокировки и засыпание потоков. Они работают на уровне инструкций процессора **CAS (Compare-And-Swap / Сравнение с обменом)**. Поток пытается обновить значение в бесконечном цикле, пока не преуспеет. Это называется **Lock-Free**.
        *Использование*: Для счетчиков задач, ID сущностей и высоконагруженных очередей, работающих на частоте кадров.

### Вопрос 2: Что такое Java Memory Model (JMM)? Какую роль играет ключевое слово `volatile` и что такое Visibility (Видимость данных)?
*   **Ответ**: 
    *   **Java Memory Model (JMM)** — это спецификация, определяющая, как потоки Java взаимодействуют через общую оперативную память. JMM описывает правила чтения и записи, а также оптимизации компилятора (кэширование переменных в регистры процессора, перестановка инструкций Out-of-Order Execution).
    *   **Visibility (Видимость)** — проблема, при которой поток $A$ обновляет переменную в RAM, но поток $B$ не видит изменений, так как читает её старое значение из своего локального кэша ядра CPU.
    *   **Ключевое слово `volatile`** гарантирует:
        1.  *Видимость*: Чтение `volatile`-переменной всегда происходит напрямую из общей RAM, а запись мгновенно сбрасывает значение в RAM, инвалидируя кэши других ядер процессора.
        2.  *Запрет перестановки (Instruction Reordering)*: Компилятор и процессор не имеют права переставлять инструкции чтения/записи через `volatile`-переменную (создается барьер памяти *Memory Barrier / Fence*).

### Вопрос 3: Как реализовать Lock-Free чтение данных чанка при асинхронном построении геометрии, если главный поток может в этот же момент перезаписывать блоки?
*   **Ответ**: 
    1.  **Копирование состояния (Snapshot)**: Перед началом построения геометрии асинхронный поток запрашивает снимок данных чанка (`getSnapshot()`). Мы копируем ссылки на текущий массив индексов блоков `short[]` и палитру. Ссылка на массив в Java атомарна.
    2.  **Защита палитры (Palette Guard)**: Запись в палитру (добавление нового блока) в главном потоке всегда оборачивается в `synchronized(paletteLock)`. При добавлении нового блока создается новая копия списка палитры (паттерн Copy-On-Write), а старая копия, которую читает асинхронный поток, остается неизменной.
    3.  **Безопасный доступ (Out-of-bounds Check)**: Асинхронный поток читает индексы из своей локальной копии массива. При обращении к палитре мы проверяем границы:
        `if (index >= localPalette.size()) return AIR;`
        Это гарантирует абсолютно непрерывную отрисовку чанка без единой блокировки главного потока (Lock-Free Read), полностью исключая краши JVM.
