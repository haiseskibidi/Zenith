# Глава 2. Графический конвейер OpenGL & Системные вызовы

В этой главе мы погрузимся в мир низкоуровневой графики. Мы разберем, как видеокарта обрабатывает трехмерные объекты, почему классические методы отрисовки перегружают центральный процессор и как устроены буферы памяти в видеопамяти (VRAM).

---

## 1. Архитектура: CPU против GPU

Перед тем как писать код рендеринга, нужно понять физическую разницу между центральным процессором (CPU) и графическим процессором (GPU).

```
   ┌───────────────────────────────────┐    ┌───────────────────────────────────┐
   │             CPU CORE              │    │             GPU CORES             │
   │  ┌───────────┐     ┌───────────┐  │    │  ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐  │
   │  │   ALU 1   │     │   ALU 2   │  │    │  └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘  │
   │  └───────────┘     └───────────┘  │    │  ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐  │
   │  ┌───────────┐     ┌───────────┐  │    │  └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘  │
   │  │   Cache   │     │ Control   │  │    │  ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐  │
   │  └───────────┘     └───────────┘  │    │  └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘ └─┘  │
   │   Мало ядер, умные, быстрые       │    │   Тысячи ядер, простые, медленные │
   └───────────────────────────────────┘    └───────────────────────────────────┘
```

*   **CPU (Central Processing Unit)**: Оптимизирован для последовательного выполнения сложных задач. Он имеет небольшое количество ядер (например, 8-16), но эти ядра невероятно мощные. У них гигантские кэши, сложнейшие предсказатели переходов и блоки управления. CPU отлично справляется с ветвлениями (`if-else`), логикой игры и работой с диском.
*   **GPU (Graphics Processing Unit)**: Оптимизирован для массовых параллельных вычислений. Он состоит из тысяч крошечных, очень простых ядер. Эти ядра не умеют быстро делать сложные ветвления, но они могут выполнять простейшие математические операции (умножение векторов, сложение чисел) над миллионами пикселей одновременно. 

3D-графика идеально ложится на параллельную архитектуру GPU. Чтобы нарисовать кадр на экране, нужно применить одни и те же математические формулы к миллионам вершин и пикселей.

## 2. Стадии графического конвейера (Rendering Pipeline)

Когда вы хотите нарисовать треугольник, данные проходят длинный путь через **конвейер отрисовки (Pipeline)**. Большинство стадий конвейера аппаратно зашиты в видеокарту, но некоторые мы можем программировать с помощью **шейдеров (Shaders)** на языке GLSL.

```
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │ Vertex Spec  ├────>│ Vertex Sh.   ├────>│ Geometry Sh. ├────>│ Rasterization│
  │ (VAO/VBO)    │     │ (Програм.)   │     │ (Опционально)│     │ (Аппаратная) │
  └──────────────┘     └──────────────┘     └──────────────┘     └──────┬───────┘
                                                                        │
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐            │
  │ Framebuffer  │<───┤ Per-Sample   │<───┤ Fragment Sh. │<───────────┘
  │ (Экран/VRAM) │     │ (Depth/Blend)│     │ (Програм.)   │
  └──────────────┘     └──────────────┘     └──────────────┘
```

1.  **Vertex Specification (Вершинная спецификация)**: Мы подготавливаем сырые данные о вершинах (координаты, цвета, текстурные координаты) в оперативной памяти и загружаем их в видеопамять GPU.
2.  **Vertex Shader (Вершинный шейдер) — `Программируемая стадия`**: Вызывается для каждой вершины. Главная задача — перевести трехмерные мировые координаты вершины $(X,Y,Z)$ в двумерное пространство экрана (так называемые *Normalized Device Coordinates / NDC* от -1.0 до 1.0) с учетом положения камеры и FOV. Результат записывается в системную переменную `gl_Position`.
3.  **Tessellation & Geometry Shaders (Шейдеры тесселяции и геометрии) — `Опционально`**: Позволяют динамически генерировать новую геометрию (например, превратить плоский полигон в детализированную гору) прямо на GPU. В воксельных движках практически не используются из-за оверхеда по производительности.
4.  **Rasterization (Растеризация) — `Аппаратная стадия`**: Видеокарта берет треугольники, собранные из вершин, и накладывает их на сетку пикселей экрана. Она определяет, какие именно пиксели покрывает треугольник, и превращает его в набор **фрагментов** (кандидатов в пиксели).
5.  **Fragment Shader (Фрагментный шейдер) — `Программируемая стадия`**: Вызывается для каждого фрагмента (пикселя), покрытого треугольником. Главная задача — вычислить финальный цвет пикселя. Здесь происходит наложение текстур, расчет освещения, тумана и теней. Результат выводится в выходной вектор (обычно `out vec4 FragColor`).
6.  **Per-Sample Operations (Тесты и смешивание) — `Аппаратная стадия`**: Видеокарта проверяет, виден ли этот пиксель игроку:
    *   **Depth Test (Тест глубины)**: Если перед этим треугольником уже нарисован другой объект ближе к камере, этот фрагмент отбрасывается.
    *   **Blending (Смешивание)**: Если объект полупрозрачный, его цвет смешивается с уже нарисованным фоном.
7.  **Framebuffer**: Финальные пиксели записываются в буфер кадра и выводятся на монитор.

## 3. Буферы данных в OpenGL (VAO, VBO, EBO, UBO)

Чтобы передать данные из Java на видеокарту, OpenGL использует специальные объекты-буферы. Давай разберем их низкоуровневую суть.

### 3.1 VBO (Vertex Buffer Object)
VBO — это просто сырой одномерный массив байт в видеопамяти GPU. В него мы записываем подряд все данные вершин.
Например, для одного треугольника VBO может выглядеть так:
`[X1, Y1, Z1, U1, V1, X2, Y2, Z2, U2, V2, X3, Y3, Z3, U3, V3]`

### 3.2 EBO / IBO (Element / Index Buffer Object)
Представь, что мы рисуем 3D-куб. Куб состоит из 6 граней, каждая грань — это 2 треугольника. Итого 12 треугольников, у каждого по 3 вершины — всего 36 вершин. Но физически у куба всего 8 углов! Это значит, что 28 вершин будут дублировать друг друга, забивая видеопамять.

Для экономии памяти используется **EBO (Буфер индексов)**:
1.  В **VBO** мы записываем только уникальные вершины (всего 8 штук для куба).
2.  В **EBO** мы записываем индексы (порядковые номера от 0 до 7) вершин, из которых видеокарта должна собрать треугольники.
    `EBO = [0, 1, 2, 2, 3, 0, ...]`

Это сокращает объем передаваемых данных более чем в 3 раза!

### 3.3 VAO (Vertex Array Object)
VBO — это просто сырые байты. Видеокарта не знает, что лежит внутри буфера: float-координаты, байты цветов или текстурные координаты. 
**VAO** — это "описатель" формата данных. Он не хранит сами вершины, он хранит настройки:
*   С каким VBO связать атрибуты.
*   Каков размер одного элемента (Stride / Шаг).
*   С какого байта начинается конкретный атрибут (Offset / Смещение).

```java
// Настройка формата вершин в Java (Mesh.java)
GL30.glBindVertexArray(vaoId); // Активируем VAO
GL15.glBindBuffer(GL15.GL_ARRAY_BUFFER, vboId); // Связываем с VBO

// Атрибут 0: Координаты (3 float, шаг 32 байта, смещение 0)
GL20.glVertexAttribPointer(0, 3, GL11.GL_FLOAT, false, 32, 0);
GL20.glEnableVertexAttribArray(0);

// Атрибут 1: Текстурные координаты (2 float, шаг 32 байта, смещение 12 байт)
GL20.glVertexAttribPointer(1, 2, GL11.GL_FLOAT, false, 32, 12);
GL20.glEnableVertexAttribArray(1);
```

### 3.4 UBO (Uniform Buffer Object)
Если нам нужно передать глобальные данные, которые одинаковы для всех вершин (например, направление солнца или матрицы камеры), мы используем UBO.
UBO позволяет один раз записать структуру данных в память GPU и "подключить" её ко всем шейдерам на определенную привязочную точку (Binding Point).

## 4. Проблема Draw Calls Bottleneck

Это самый главный враг графической производительности. 

Когда центральный процессор (CPU) вызывает метод отрисовки `glDrawElements()`, происходит **Draw Call**. 
1.  CPU проверяет все стейты (состояния) OpenGL.
2.  Конвертирует Java-команду в формат системного вызова драйвера видеокарты.
3.  Драйвер отправляет команду в ядро операционной системы, а затем по шине PCIe — на видеокарту.

Если в твоей сцене 2000 мелких объектов, и ты рисуешь их классическим циклом (2000 вызовов `glDrawElements`), твой CPU будет тратить 95% времени на обслуживание драйвера. Видеокарта при этом будет спать, загруженная на 10-15%, так как она обрабатывает миллионы треугольников за микросекунды, а новые команды от CPU приходят слишком медленно.

### 4.1 Переключение состояний (State Changes)
Еще хуже, если между отрисовками объектов ты меняешь настройки:
`Bind Shader 1 -> Bind Texture A -> Draw -> Bind Shader 2 -> Bind Texture B -> Draw ...`

Каждый вызов `glBindTexture` или `glUseProgram` заставляет видеокарту сбрасывать свой конвейер (**Pipeline Stall**). Ядра GPU вынуждены останавливать вычисления, ждать, пока очистятся их внутренние кэши текстур, загружать новые настройки и только потом возобновлять работу. 

> [!IMPORTANT]
> **Золотое правило графического инженера**: Минимизируй количество Draw Calls и переключений состояний! Рисуй как можно больше геометрии за один вызов, используя батчинг.

## 5. Основы GLSL (OpenGL Shading Language)

Шейдеры пишутся на языке GLSL. Синтаксис очень похож на Си.
Давай разберем простейшую пару вершинного и фрагментного шейдеров.

### Вершинный шейдер (`simple_vertex.glsl`)
```glsl
#version 330 core

// Входные атрибуты из VAO (описаны в Java)
layout(location = 0) in vec3 aPos;
layout(location = 1) in vec2 aTexCoords;

// Выходные данные для передачи во фрагментный шейдер
out vec2 TexCoords;

// Глобальные константы, одинаковые для всего кадра
uniform mat4 uProjectionView;
uniform mat4 uModel;

void main() {
    // Вычисляем финальную позицию вершины на экране
    gl_Position = uProjectionView * uModel * vec4(aPos, 1.0);
    
    // Передаем текстурные координаты дальше по конвейеру
    TexCoords = aTexCoords;
}
```

### Фрагментный шейдер (`simple_fragment.glsl`)
```glsl
#version 330 core

// Входные данные (приходят из вершинного шейдера, интерполированные по треугольнику)
in vec2 TexCoords;

// Финальный выходной цвет пикселя
out vec4 FragColor;

// Текстурный сэмплер
uniform sampler2D uTexture;

void main() {
    // Выбираем цвет пикселя из текстуры по координатам TexCoords
    vec4 texColor = texture(uTexture, TexCoords);
    
    // Если пиксель полностью прозрачный — отбрасываем фрагмент (Alpha Cutout)
    if (texColor.a < 0.1) {
        discard; 
    }
    
    FragColor = texColor;
}
```

> [!NOTE]
> Обрати внимание: фрагментный шейдер получает данные `TexCoords` не напрямую. Вершинный шейдер запускается 3 раза для треугольника (для 3 углов). Растеризатор берет эти 3 разные координаты `TexCoords` и **плавно интерполирует (сглаживает)** их для каждого пикселя внутри треугольника перед запуском фрагментного шейдера.

## 6. Подготовка к собеседованию (IT-Шпаргалка)

### Вопрос 1: В чем разница между VAO и VBO в OpenGL? Какие задачи решает каждый из них?
*   **Ответ**: 
    *   **VBO (Vertex Buffer Object)** — это буфер данных в видеопамяти GPU, который хранит сырой массив байт (координаты вершин, нормали, цвета, текстурные координаты). VBO отвечает за **хранение** данных.
    *   **VAO (Vertex Array Object)** — это объект состояния, который хранит информацию о **формате** данных внутри VBO. Он описывает, как интерпретировать сырые байты: указывает индексы вершинных атрибутов, их типы (`float`, `int`), смещения (offsets) и шаг (stride). VAO связывает конкретные атрибуты шейдера с данными в VBO.
    *   На практике мы привязываем VAO один раз перед отрисовкой (`glBindVertexArray`), что автоматически настраивает все указатели на буферы VBO, избавляя от необходимости вызывать тяжелые методы настроек формата на каждом кадре.

### Вопрос 2: Что такое Draw Calls Bottleneck и Pipeline Stall? Как они влияют на FPS?
*   **Ответ**: 
    *   **Draw Call Bottleneck** возникает, когда центральный процессор (CPU) перегружен отправкой команд отрисовки (`glDrawElements`) в драйвер видеокарты. Видеокарта при этом простаивает, ожидая новые инструкции. Это приводит к падению FPS при малом использовании GPU.
    *   **Pipeline Stall (срыв конвейера)** происходит при частом переключении состояний графического API (смена шейдера `glUseProgram`, бинд текстур `glBindTexture` или изменение настроек блендинга). При смене состояния ядра GPU вынуждены останавливать параллельные вычисления, сбрасывать внутренние кэши и конвейеры команд, чтобы применить новые настройки. Это приводит к микросекундным задержкам, снижающим общую плавность рендеринга.

### Вопрос 3: Зачем нужен Depth Test (Тест глубины) и как оптимизировать рендеринг прозрачных и непрозрачных объектов?
*   **Ответ**: Depth Test автоматически проверяет координату $Z$ фрагмента с использованием **Depth Buffer (Z-буфера)**. Если новый фрагмент находится дальше от камеры, чем уже нарисованный в этой точке пиксель, фрагмент отбрасывается.
*   **Оптимизация порядка отрисовки**:
    1.  **Непрозрачные объекты (Opaque Pass)** нужно рисовать **в первую очередь**, сортируя их **от ближних к дальним** (Front-to-Back). Это включает оптимизацию *Early-Z Culling* на GPU: видеокарта будет мгновенно отбрасывать дальние фрагменты, скрытые за ближними стенами, не запуская для них тяжелые фрагментные шейдеры (предотвращает *Overdraw*).
    2.  **Прозрачные объекты (Translucent Pass)** нужно рисовать **в последнюю очередь** с выключенной записью в Z-буфер (`glDepthMask(false)`) и включенным блендингом. При этом их обязательно нужно сортировать **от дальних к ближним** (Back-to-Front), чтобы смешивание цветов происходило физически корректно.
