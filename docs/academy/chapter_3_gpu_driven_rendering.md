# Глава 3. GPU-Driven Rendering & Оптимизация VRAM

В этой главе мы разберем вершину графической инженерии движка Zenith v2.0 — **GPU-Driven рендеринг**. Вы узнаете, как избавиться от тысяч переключений буферов в кадре, как заставить видеокарту самостоятельно читать команды отрисовки из VRAM и как сжать геометрические данные до предела.

---

## 1. Парадигма GPU-Driven Рендеринга

В традиционной архитектуре рендеринга центральный процессор (CPU) жестко контролирует каждый шаг видеокарты: он определяет, какой меш рисовать, связывает буферы, передает матрицы и вызывает отрисовку.

В **GPU-Driven** подходе мы отдаем контроль видеокарте. CPU занимается лишь высокоуровневым планированием (например, BFS-обходом видимости чанков) и формированием команд, а сама отрисовка, выборка геометрии из пула и применение трансформаций происходят на GPU практически без участия процессора.

Это достигается за счет связки трех технологий:
1.  **Centralized Mesh Pooling** (Глобальный пул мешей).
2.  **Indirect Drawing** (Непрямая отрисовка).
3.  **MultiDraw Batching** (Групповые вызовы).

---

## 2. Архитектура Mesh Pooling в Zenith

В классических играх для каждого воксельного чанка создается свой отдельный Vertex Buffer (VBO) и Index Buffer (IBO). В мире из 1000 чанков видеокарте приходится каждую секунду делать тысячи вызовов `glBindBuffer()` и `glBindVertexArray()`, что приводит к фрагментации видеопамяти (VRAM) и тормозам шины PCIe.

В Zenith v2.0 мы внедрили класс `MeshPool` — **Глобальный пул мешей**.

```
  ┌────────────────────────────────────────────────────────┐
  │                 MeshPool VRAM (1.5 GB)                 │
  ├────────────────────────────────────────────────────────┤
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
  │  │ Chunk 1  │  │ Chunk 2  │  │ Chunk 3  │   ... Свобод │
  │  │ (Alloc)  │  │ (Alloc)  │  │ (Alloc)  │   ... Память │
  │  └──────────┘  └──────────┘  └──────────┘              │
  └────────────────────────────────────────────────────────┘
   Один гигантский VBO/EBO. 0 переключений буферов в кадре!
```

### 2.1 Как устроен `MeshPool`
При старте движок выделяет в VRAM один гигантский буфер (например, 1.5 ГБ) под VBO и EBO. 
Когда чанк генерирует свою воксельную геометрию:
1.  Вместо создания нового VBO он запрашивает блок памяти у `MeshPool`.
2.  `MeshPool` находит свободный непрерывный кусок памяти нужного размера (используя алгоритмы аллокации, похожие на работу кучи в C++).
3.  Записывает вершины чанка непосредственно в этот глобальный буфер по определенному смещению.
4.  Чанку возвращается объект `Mesh`, содержащий `baseVertex` (индекс первой вершины в глобальном пуле) и `firstIndex` (начальный индекс треугольника).

Во время отрисовки мы привязываем глобальный VAO пула **ровно один раз** за кадр!

### 2.2 Версионирование пула (Pool Versioning & Safety)
Что происходит, когда в мире постоянно ломаются блоки, чанки перестраиваются, а свободное место в конце пула заканчивается?
`MeshPool` использует кольцевой буфер (wrap-around): при достижении конца буфера новые данные начинают записываться в самое начало, затирая старые, давно выгруженные чанки.

Но возникает смертельная опасность: если старый чанк все еще стоит в очереди на рендеринг, а его вершины в начале буфера уже затерты новыми данными, на экране возникнет визуальная "каша" (координаты перепутаются).

Для предотвращения этого в Zenith внедрена **система версионирования (Pool Versioning)**:
*   Каждый раз, когда указатель записи в `MeshPool` переходит через границу буфера (Wrap-around), глобальный счетчик `poolVersion` инкрементируется на 1.
*   Каждый меш чанка хранит версию пула, в которой он был создан (`mesh.poolVersion`).
*   Перед отрисовкой `RenderPipeline` сравнивает версию меша с текущей версией пула. Если они отличаются, меш автоматически помечается как **инвалидный**, его данные мгновенно пересобираются в асинхронном потоке и записываются в новое, актуальное поколение пула.

## 3. MultiDraw Indirect (MDI) в деталях

Теперь разберем, как нарисовать все чанки из глобального пула за 1 системный вызов.

В OpenGL 4.3+ существует семейство функций непрямой отрисовки. В Java (через LWJGL 3) мы вызываем:
```java
GL43.glMultiDrawElementsIndirect(
    GL11.GL_TRIANGLES, 
    GL11.GL_UNSIGNED_INT, 
    0,                  // Смещение в Indirect Buffer
    commandCount,       // Количество команд
    0                   // Шаг между командами
);
```

### 3.1 Структура команды (Indirect Command Layout)
Команда отрисовки одного объекта в Indirect Buffer — это структура из 5 целых чисел (20 байт):
```glsl
struct DrawElementsIndirectCommand {
    uint count;         // Кол-во индексов треугольников (например, 36 для куба)
    uint instanceCount; // Кол-во инстансов (копий) (для чанков обычно 1)
    uint firstIndex;    // Смещение начала в глобальном EBO (индексы)
    uint baseVertex;    // Смещение начала в глобальном VBO (вершины)
    uint baseInstance;  // Смещение в буфере данных инстансов
};
```

### 3.2 Оркестратор `MultiDrawBatch`
В Zenith за группировку команд отвечает класс `MultiDrawBatch`:
1.  Каждый кадр `ChunkRenderSystem` сканирует видимые чанки (после Cave Culling).
2.  Для каждого видимого чанка мы вызываем `batch.put(mesh)`.
3.  `MultiDrawBatch` записывает 20-байтную команду `DrawElementsIndirectCommand` во временный буфер в оперативной памяти Java (`ByteBuffer`).
4.  В конце фазы сбора `MultiDrawBatch` копирует весь сформированный массив команд в VRAM видеокарты в специальный буфер **`GL_DRAW_INDIRECT_BUFFER`** с помощью быстрого вызова `glBufferSubData`.
5.  Вызывается `glMultiDrawElementsIndirect`. Видеокарта считывает этот массив команд из своей памяти и мгновенно, параллельно запускает отрисовку тысяч чанков. CPU при этом полностью свободен!

## 4. Битовая упаковка вершин Standard Mesh (v1.1)

Чтобы VRAM не забивалась терабайтами геометрии, вершина в Zenith v1.1 сжата до **28 байт** (вместо стандартных 48-64 байт).
Один float в Java занимает 4 байта (32 бита). Но для многих параметров (например, нормали куба или текстурной координаты 0-1) 32 бита — это расточительство. Мы упаковываем несколько значений в биты одного `int` / `uint`.

### Структура сжатой вершины:
*   **uint aPackedData0 (32 бита)**:
    *   `Бит 0-9`: Координата X вокселя в чанке (разрешение 1024 делений для плавных суб-блочных смещений).
    *   `Бит 10-19`: Координата Y вокселя (0-256).
    *   `Бит 20-29`: Координата Z вокселя.
    *   `Бит 30-31`: Зарезервировано.
*   **uint aPackedData1 (32 бита)**:
    *   `Бит 0-4`: Текстурная координата U (масштабированная от 0 до 16).
    *   `Бит 5-9`: Текстурная координата V.
    *   `Бит 10-15`: Индекс слоя массива текстур (0-63).
    *   `Бит 16-23`: Индекс нормали куба (0-5 для шести осей).
    *   `Бит 24-31`: Вес ветра для анимации sway (0.0 - 2.0 с шагом 0.01).

### Распаковка в `vertex.glsl`:
```glsl
#version 330 core

layout(location = 0) in uint aPackedData0;
layout(location = 1) in uint aPackedData1;

out vec3 vNormal;
out vec3 vUVW;
out float vWindWeight;

const vec3 NORMALS[6] = vec3[](
    vec3( 0,  1,  0), // Вверх
    vec3( 0, -1,  0), // Вниз
    vec3( 1,  0,  0), // Право
    vec3(-1,  0,  0), // Лево
    vec3( 0,  0,  1), // Вперед
    vec3( 0,  0, -1)  // Назад
);

void main() {
    // 1. Распаковка координат X, Y, Z (масштаб 1/16 блока)
    float x = float(aPackedData0 & 0x3FFu) / 16.0;
    float y = float((aPackedData0 >> 10) & 0x3FFu) / 16.0;
    float z = float((aPackedData0 >> 20) & 0x3FFu) / 16.0;
    vec3 localPos = vec3(x, y, z);
    
    // 2. Распаковка текстурных координат и слоя
    float u = float(aPackedData1 & 0x1Fu) / 16.0;
    float v = float((aPackedData1 >> 5) & 0x1Fu) / 16.0;
    float w = float((aPackedData1 >> 10) & 0x3Fu); // Слой 2DArray
    vUVW = vec3(u, v, w);
    
    // 3. Распаковка нормали
    uint normalIdx = (aPackedData1 >> 16) & 0xFFu;
    vNormal = NORMALS[normalIdx];
    
    // 4. Распаковка веса ветра
    vWindWeight = float((aPackedData1 >> 24) & 0xFFu) / 100.0;
    
    gl_Position = uProjectionView * vec4(localPos, 1.0);
}
```

## 5. Connected Textures & Dynamic Smooth Lighting

Воксельные кубики без сглаживания выглядят плоско. Для создания красивых переходов на стыках блоков Zenith использует алгоритмы Connected Textures (CTM) и Smooth Lighting.

### 5.1 Алгоритм Connected Textures (Соединение текстур)
Когда рядом стоят два одинаковых блока (например, стекло к стеклу), мы не хотим видеть внутреннюю сетку швов рамки.
1.  При генерации меша чанка генератор проверяет 8 соседей на плоскости грани.
2.  Формируется битовая маска смежностей (от 0 до 255).
3.  На основе маски рассчитывается смещение UV-координат. Видеокарта автоматически подставляет нужный сегмент бесшовной текстуры (уголок, рамка, центр).

### 5.2 Dynamic Smooth Lighting & Ambient Occlusion (AO)
Для мягких теней в углах комнат мы рассчитываем освещенность четырех вершин каждой грани куба на основе уровня света соседних блоков:

```
  ┌───────────────┬───────────────┐
  │  Сосед B1     │  Сосед B2     │
  │  (Light 12)   │  (Light 8)    │
  ├───────────────┼───────────────┤
  │               │ Вершина V (AO)│  <-- Вычисляем свет в этой точке
  │               │ (Тут стык)    │
  └───────────────┴───────────────┘
   Итоговый свет V = (Light_Self + B1 + B2 + Corner) / 4
```

Для каждой вершины $V$ мы опрашиваем значения блочного и солнечного света в трех смежных блоках, образующих угол, и берем среднее арифметическое.

#### Проблема: Вспышки света при разрушении блоков (Breaking Guards)
Когда игрок ломает блок дерева, в процессе майнинга этот блок физически все еще находится в мире. Но алгоритмы освещения при каждом ударе перестраивают меши соседних чанков. 

Если соседний меш считает, что разрушаемый блок дерева "уже исчез", он мгновенно рассчитывает яркий солнечный свет на стыке. Грани соседней листвы начинают хаотично вспыхивать белым и черным цветом при каждом ударе инструмента.

**Решение в Zenith**:
Мы внедрили класс `ShaderStateManager` и защиту `Breaking Guards`. При пересчете освещения во время анимации добычи генератор меша считывает позицию разрушаемого блока `breakingPos` и принудительно подменяет её в алгоритме:
```java
// Внутри ChunkNeighborhood.java при расчете AO
if (neighborPos.equals(world.getBreakingPos())) {
    // Считать, что на этой позиции все еще находится дерево (применяем его прозрачность),
    // предотвращая резкий пересчет солнечного света до реального исчезновения блока.
}
```
Это полностью устранило визуальное мерцание листвы и камней, сделав переходы освещения абсолютно плавными.

## 6. Подготовка к собеседованию (IT-Шпаргалка)

### Вопрос 1: Объясните концепцию GPU-Driven рендеринга и отличие от CPU-Driven. Какие технологии OpenGL это обеспечивают?
*   **Ответ**: 
    *   В **CPU-Driven** архитектуре процессор на каждом кадре совершает итерацию по объектам, проверяет их видимость, связывает текстуры/буферы и отправляет индивидуальные команды отрисовки (`glDrawElements`), что перегружает CPU (Draw Call Bottleneck).
    *   В **GPU-Driven** архитектуре процессор лишь один раз загружает всю геометрию в глобальный пул, а затем передает массив команд отрисовки непосредственно в буфер видеокарты. Видеокарта сама считывает эти команды и рисует тысячи объектов параллельно.
    *   Эту парадигму обеспечивают три ключевые технологии:
        1.  **Mesh Pooling**: Единый гигантский VBO/IBO для хранения всей геометрии, убирающий переключение буферов кадра.
        2.  **Indirect Buffers (`GL_DRAW_INDIRECT_BUFFER`)**: Буферы в VRAM, хранящие структуры параметров команд отрисовки.
        3.  **MultiDraw Indirect (`glMultiDrawElementsIndirect`)**: Вызов графического API, позволяющий выполнить весь буфер indirect-команд за один вызов.

### Вопрос 2: Зачем нужна система версионирования в Mesh Pool (`poolVersion`) и к каким багам приведет её отсутствие?
*   **Ответ**: `MeshPool` работает по принципу циклического буфера (Wrap-around): при заполнении буфера новые чанки записываются в начало, затирая старую геометрию. 
*   Система версионирования `poolVersion` отслеживает поколения записи буфера. Каждый меш хранит версию своего поколения. Перед отрисовкой рендерер сверяет версию меша с текущей версией пула.
*   **Если версионирования нет**: Если старый чанк все еще стоит в очереди на отрисовку (или драйвер видеокарты не успел завершить предыдущий кадр), а его физическая память в буфере уже затерта новым сгенерированным чанком, видеокарта считает некорректные координаты вершин. Это приведет к критическому визуальному багу — "визуальной каше" на экране (геометрия чанков перепутается, возникнут дикие растянутые треугольники сквозь всю карту).

### Вопрос 3: Как реализовать сжатие вершин воксельного мира на уровне битовых сдвигов и распаковать их в GLSL шейдере?
*   **Ответ**: Вместо использования стандартных float-типов (4 байта на координату), мы используем битовую упаковку в целые числа `uint` (32 бита).
*   В Java мы сдвигаем биты локальных координат (0-16 с точностью до 1/16 блока, требующих 10 бит) и упаковываем их в битовые поля одного `int`:
    `int packed = (x & 0x3FF) | ((y & 0x3FF) << 10) | ((z & 0x3FF) << 20);`
*   В GLSL-шейдере мы объявляем входные параметры как `layout(location = 0) in uint aPackedData;`.
*   Распаковка в шейдере происходит с помощью битовых масок и сдвигов:
    `float x = float(aPackedData & 0x3FFu) / 16.0;`
    `float y = float((aPackedData >> 10) & 0x3FFu) / 16.0;`
    `float z = float((aPackedData >> 20) & 0x3FFu) / 16.0;`
    Это позволяет сжать вершину до 28 байт, экономя пропускную способность шины PCIe и VRAM.
