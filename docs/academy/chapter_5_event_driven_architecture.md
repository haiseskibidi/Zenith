# Глава 5. Реактивная шина событий & Архитектура ввода

В этой главе мы разберем, как построить чистую, слабосвязанную архитектуру (Decoupled Architecture) игрового движка. Мы изучим, как реактивная шина событий **EventBus** избавляет от спагетти-кода, как обрабатывать пользовательский ввод без выделения памяти и как устроен контроллер интерактивной добычи блоков.

---

## 1. Проблема сильной связанности (Tight Coupling)

В плохо спроектированных игровых движках класс ввода клавиатуры выглядит так:
```java
// Ужасный спагетти-код
public void handleKeyW() {
    player.physics.walkForward();
    soundManager.playFootstep();
    ui.minimap.updatePosition();
    if (world.getBiome(player.pos) == Biomes.swamp) {
        particleManager.spawnMudSplashes();
    }
}
```
Этот класс знает о существовании физики, звуков, интерфейса, биомов и частиц! Если вы захотите изменить звук шага, вам придется лезть в класс ввода. Если вы удалите миникарту, код ввода перестанет компилироваться. Это называется **сильной связанностью**.

В Zenith v2.5 мы применили два паттерна для полной развязки систем:
1.  **InputAction Layer** (Абстракция ввода).
2.  **EventBus** (Реактивная шина событий).

---

## 2. Zero-Alloc InputAction Layer

Мы полностью запретили использовать сырые коды клавиш GLFW (`GLFW_KEY_W`, `GLFW_KEY_SPACE`) внутри игровой логики. Вместо этого ввод делится на два этапа.

```
  Клавиатура (GLFW)         Битовый Массив (long[])         Логический Экшен
  ┌─────────────────┐       ┌──────────────────────┐       ┌─────────────────┐
  │  Key W Pressed  ├──────>│  [00010000 00000000] ├──────>│  "move_forward" │
  │  Space Pressed  │       └──────────────────────┘       │  "jump"         │
  └─────────────────┘        Zero-Alloc Состояния          └─────────────────┘
```

### 2.1 Логические действия (`InputAction`)
Мы объявили перечисление `InputAction`, описывающее намерения игрока:
`MOVE_FORWARD, MOVE_BACKWARD, JUMP, INTERACT, OPEN_JOURNAL, ATTACK`

Связь между физической клавишей и логическим экшеном задается в настройках (`options.json`) и загружается в `SettingsManager`. 

### 2.2 Битовые буферы состояний (Zero-Alloc Input)
Чтобы опрашивать состояние клавиш каждый кадр без выделения объектов Java, `InputManager` использует примитивные плоские битовые массивы `long[]`:
*   `isPressed` — зажата ли клавиша сейчас.
*   `wasJustPressed` — была ли нажата строго в этом кадре.
*   `wasJustReleased` — была ли отпущена строго в этом кадре.

Один примитив `long` хранит 64 бита. Так как общее количество отслеживаемых игровых клавиш меньше 64, **все состояние клавиатуры и мыши умещается в три примитивных числа `long`!**

```java
// com.za.zenith.engine.input.InputManager.java
public class InputManager {
    private long pressedMask = 0L;
    private long justPressedMask = 0L;
    private long justReleasedMask = 0L;

    // Вызывается GLFW коллбэком при клике клавиши
    public void onKeyCallback(int actionId, int actionType) {
        long bit = 1L << actionId; // Вычисляем маску бита
        
        if (actionType == GLFW.GLFW_PRESS) {
            pressedMask |= bit;
            justPressedMask |= bit;
        } else if (actionType == GLFW.GLFW_RELEASE) {
            pressedMask &= ~bit;
            justReleasedMask |= bit;
        }
    }

    // Опрос состояния в игровом цикле
    public boolean isActionPressed(InputAction action) {
        int keyIndex = SettingsManager.getInstance().getBind(action);
        return (pressedMask & (1L << keyIndex)) != 0L; // Мгновенная битовая проверка!
    }

    // Вызывается в конце кадра для сброса триггеров "Just"
    public void clearFrameStates() {
        justPressedMask = 0L;
        justReleasedMask = 0L;
    }
}
```
**Результат**: 0 объектов в памяти, 0 обращений к куче, мгновенный побитовый опрос состояний.

## 3. Реактивная шина событий (EventBus)

Для связи независимых систем мы внедрили шаблон **Publish-Subscribe (Издатель-Подписчик)** через класс `EventBus`.

```
                  ┌──────────────────────┐
                  │       EventBus       │
                  └──────────┬───────────┘
         Публикация          │           Рассылка события
         события             ▼           подписчикам
  ┌─────────────────┐  ┌───────────┐  ┌───────────────────────┐
  │  Input Handler  ├──>│ BlockLeft │─>│ MiningController      │
  │  (Клик ПКМ)     │  │ ClickEvent│  ├───────────────────────┤
  └─────────────────┘  └───────────┘  │ ParticleManager       │
                                      └───────────────────────┘
```

### 3.1 Архитектура `EventBus`
Шира событий хранит списки слушателей (подписчиков), сгруппированных по классам событий.
```java
// com.za.zenith.engine.event.EventBus.java
public class EventBus {
    private static final Map<Class<? extends Event>, List<Consumer<? extends Event>>> listeners = new ConcurrentHashMap<>();

    // Подписка на событие
    public static <T extends Event> void subscribe(Class<T> eventClass, Consumer<T> listener) {
        listeners.computeIfAbsent(eventClass, k -> new CopyOnWriteArrayList<>()).add(listener);
    }

    // Публикация события (Рассылка всем подписчикам)
    @SuppressWarnings("unchecked")
    public static <T extends Event> void post(T event) {
        List<Consumer<? extends Event>> eventListeners = listeners.get(event.getClass());
        if (eventListeners == null) return;
        
        for (Consumer<? extends Event> listener : eventListeners) {
            ((Consumer<T>) listener).accept(event);
        }
    }
}
```

### 3.2 Разделение обязанностей (Decoupled Controllers)
Благодаря `EventBus` мы полностью очистили обработчики ввода. Класс `InteractionInputHandler` при клике ЛКМ по блоку делает ровно одну вещь:
`EventBus.post(new BlockLeftClickEvent(player, targetBlockPos, face));`

В этот момент активируются независимые контроллеры-подписчики:
1.  **`MiningController`**: перехватывает событие, наносит физический урон блоку, запускает таймер кулдауна.
2.  **`ParticleManager`**: перехватывает это же событие, определяет тип блока и спавнит сочные частицы щепок на месте удара.
3.  **`SoundManager`**: проигрывает звук глухого удара по дереву или звона металла по камню.

Если мы решим добавить в игру статистику "Сколько раз игрок ударил по дереву", мы просто создадим `StatsController` и подпишем его на `BlockLeftClickEvent`. **Нам не придется менять ни строчки в коде ввода или физики блоков!**

## 4. Геймплейная логика: MiningController & Weak Spots

Механика добычи в Zenith v2.1 — это интерактивный игровой процесс, управляемый классом `MiningController`.

### 4.1 Алгоритм слабых точек (Weak Spots)
При ударе по блоку дерева или автомобиля на его грани генерируется процедурная мишень (Weak Spot):
1.  **Рейкаст**: Движок пускает луч из камеры игрока в мир. Метод `raycast` находит пересекаемый блок и точную **нормаль грани** (какая сторона куба выбрана: верхняя, боковая и т.д.).
2.  **Генерация на плоскости**: Мы проецируем точку попадания луча в 2D плоскость грани блока. В этой плоскости процедурно генерируются координаты круглой мишени Weak Spot.
3.  **Смена грани в реальном времени**: Если игрок продолжает зажимать кнопку удара, но перебегает на другую сторону куба, `MiningController` фиксирует смену нормали грани и мгновенно перегенерирует слабую точку на новой грани перед глазами игрока, чтобы сохранить динамику.

```java
// Внутри MiningController.java при ударе по блоку
float damage = baseToolDamage;
if (hitHistory.isPointInsideWeakSpot(raycastHit.localUV)) {
    damage *= 3.0f; // Тройной критический урон!
    ParticleManager.getInstance().spawnImpactParticles(pos, face, 15); // Много опилок
    World.java.recordPersistentScar(pos, 1.0f); // Глубокая зарубка
} else {
    damage *= 0.2f; // Штраф за промах
    ParticleManager.getInstance().spawnImpactParticles(pos, face, 2); // Пара щепок
}
blockHealth -= damage;
```

### 4.2 Визуальные шрамы (Persistent Scars) & Wobble
Успешные попадания по слабым точкам записываются в `blockDamageMap` мира в виде структуры `BlockDamageInstance`. Мы передаем в шейдер оверлеев `breaking_patterns.glsl` координаты и интенсивность зарубки в векторе `Vector4f` (где компонента `w` отвечает за прозрачность зарубки).
*   **Wobble-эффект**: При ударе по блоку создается прокси-меш блока. Рендерер трясет его по синусоиде во время удара, заставляя обводку блока колыхаться в такт физическому отклику.
*   **Smooth Healing (Затягивание шрамов)**: Если игрок перестал бить блок, через 5 секунд в `World.update()` запускается алгоритм плавного лечения: здоровье блока регенерирует, а интенсивность шрама `w` плавно снижается до 0 в течение 2 секунд.

## 5. Подготовка к собеседованию (IT-Шпаргалка)

### Вопрос 1: Что такое шаблон проектирования EventBus (шина событий)? Каковы его достоинства и недостатки в крупных архитектурах?
*   **Ответ**: 
    *   **EventBus** — это реализация паттерна *Publish-Subscribe (Издатель-Подписчик)*. Он служит центральным каналом связи, позволяющим различным компонентам системы взаимодействовать друг с другом без явного знания о существовании друг друга (обеспечивает слабую связанность / Loose Coupling).
    *   **Достоинства**:
        1.  *Упрощение расширения*: Легко добавлять новые функции (например, логгер, достижения, звуки), просто подписываясь на существующие события.
        2.  *Тестируемость*: Системы изолированы, их можно тестировать юнит-тестами независимо от других слоев.
        3.  *Чистота кода*: Классы ввода или физики освобождаются от геймплейных зависимостей.
    *   **Недостатки**:
        1.  *Сложность отладки (Debugging)*: Потеря цепочки вызовов (Stack Trace). Нельзя нажать `Ctrl+Click` на метод, чтобы увидеть, кто его вызвал — поток управления прерывается отправкой события в шину.
        2.  *Производительность*: При неосторожной реализации рассылка событий через рефлексию или создание тысяч временных объектов событий в секунду нагружает кучу и сборщик мусора JVM.
        3.  *Потокобезопасность*: Если события публикуются из асинхронных потоков, шина должна корректно синхронизировать списки подписчиков.

### Вопрос 2: Как спроектировать высокопроизводительную Zero-Alloc систему опроса ввода клавиатуры в JVM?
*   **Ответ**: 
    *   Для полной ликвидации выделения памяти в цикле ввода (Zero-Allocation) необходимо отказаться от хранения состояний клавиш в коллекциях объектов (`Map<Integer, Boolean>` или `Set<Integer>`), так как автобоксинг примитивных ID клавиш и выделение нод коллекций перегружают GC.
    *   Вместо этого состояние клавиатуры и мыши кодируется битовыми масками внутри примитивных типов `long` (поскольку кодов GLFW-клавиш немного, а один `long` вмещает 64 независимых состояния).
    *   Мы создаем три маски: `pressedMask` (активные зажатые клавиши), `justPressedMask` (клавиши, нажатые строго в текущем кадре) и `justReleasedMask` (отпущенные в этом кадре).
    *   В GLFW Key Callback мы устанавливаем или сбрасываем биты масок с помощью быстрых побитовых операций:
        `pressedMask |= (1L << keyId);` — установить бит при нажатии.
        `pressedMask &= ~(1L << keyId);` — сбросить бит при отпускании.
    *   Опрос состояния логических экшенов (`InputAction`) происходит мгновенным побитовым умножением без аллокаций:
        `boolean active = (pressedMask & (1L << keyIndex)) != 0L;`

### Вопрос 3: Опишите алгоритм работы механики Weak Spots (Слабых точек) при добыче воксельных блоков. Как связать физику процесса с визуальными эффектами?
*   **Ответ**: 
    1.  **Raycast**: Движок пускает луч из камеры игрока вдоль направления взгляда. Мы находим пересекаемый AABB блока, координаты точки коллизии и вектор нормали грани куба (Direction face).
    2.  **Проекция в UV**: Мы переводим трехмерные координаты точки коллизии в двумерные локальные координаты грани $(u, v)$ в диапазоне от 0.0 до 1.0.
    3.  **Генерация цели**: При первом ударе в плоскости $(u, v)$ процедурно задается координата центра круглой слабой точки $(cx, cy)$ и радиус $R$.
    4.  **Проверка попадания**: При последующих ударах мы вычисляем евклидово расстояние от точки клика до центра мишени:
        $$\text{dist} = \sqrt{(u - cx)^2 + (v - cy)^2}$$
        Если $\text{dist} \le R$, удар считается точным. Блоку наносится критический урон, а на месте удара генерируется сноп частиц осколков с текстурой текущей грани.
    5.  **Визуальная связь**: Данные точного удара записываются в `blockDamageMap` мира в виде вектора `Vector4f` (координаты скола в компонентах XYZ, интенсивность шрама в компоненте W) и передаются в шейдер для наложения персистентных зарубок.
